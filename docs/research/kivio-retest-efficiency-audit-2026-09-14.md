## 已定位的精简回归：历史占位参数进入新调用并实际写盘

初次核查只统计了返回体和受保护参数，遗漏了本次第47轮已经发生的文件污染。这是比后文执行效率问题更优先的确定缺陷。

1. `e61b15d4`新增`argument_replay.rs`，把部分已完成write/edit调用的content/old_string/new_string替换成`[Kivio history: completed file payload omitted; …]`字符串，再以原来的工具调用结构发给模型。占位符仍是合法字符串，仍处在可执行参数的位置。
2. 本次第47轮新write调用`call_00_5XwMee6DjqCtFaITvVsG2949`，目标为此前尚未创建的`tests/test_api.py`，其content本身就是上述占位符，声称省略20880字节。保存的arguments和arguments_raw均为319字节左右的占位调用，没有原始测试代码。
3. 该次工具返回success。structured_content.bytes_written为253，diff只有一行占位文字。第48轮`wc -l`为0，`head`读回同一占位文字，证明文件确实受到污染，不是界面隐藏正文。
4. 第49轮的后续分析明确认为写入被环境省略，转而选择每块约7KB，以`# __PART2__`作锚点连续edit拼接，并额外担心此前大文件是否也被破坏。第49–57轮包含重建API测试及相关修改，其中49、51、52、54、55、56、57共七次写入/编辑该测试文件。不能将该区间所有工作都算为纯额外开销。

问题发生在模型可见的历史表示和执行边界：程序把曾经的“真实写入参数”改造成“拿占位文字调用write”的示例，而执行器又允许同样的占位文字进入新文件。提示符中的“do not execute”不是执行约束。

代码检查显示精简入口处理发送副本，规划阶段从新响应提取待执行调用，尚无证据证明同一份原始20KB响应被本地代码直接截断成占位符；也没有保存这次请求的原始网络响应可用于证明逐字来源。因此准确结论是：占位标记已经进入新的执行参数并落盘，且后续分块/复查策略明确由此触发。不能进一步假称找到了内存别名覆盖，也不能把全部69次新增请求或Playwright误判都归到这一处。

本次完整日志中没有bash输出落盘截断标记；两次均没有上下文摘要压缩边界。这些路径不能作为本次已观察到的文件污染原因。新旧代码中shell未启用pipefail的问题也早已存在，不是此次精简引入。

修复优先级：首先停止在可执行参数字段里植入省略占位符，并拒绝把这种历史标记作为新write正文或edit替换正文；保留简短工具回执和独立的完整审阅数据。然后处理日志、能力探测和验证复用。继续缩小reasoning保护范围会让更多历史调用变成占位示例，当前不应先做。

原测试`native_file_receipts_are_short_on_the_wire_and_keep_review_diff`使用预设模型响应，只验证发送体更短、磁盘和审阅历史完整；它不会根据收到的历史生成下一步，因而没有覆盖“下轮新调用带回占位符”的路径。需要额外覆盖这一执行边界，并对真实模型行为做受控复测。

## 扩展审计：另两项实报链路缺陷与edit影响范围

用真实native文件执行器、本地HTTP模型夹具、现有请求指纹与显示选择函数运行三个最小诊断测试。命令为`cargo test --lib audit_efficiency_ -- --ignored --nocapture`，三项断言均按预期暴露缺陷（0通过、3失败，执行0.06秒）。临时用例已从源码移至`.scratch/issue-51/extended-audit-agent-tests.rs`与`extended-audit-command-tests.rs`；完整输出在`extended-audit-red.log`，生产逻辑未改动。

### A. 同一污染漏洞也允许edit破坏已有代码

临时文件原为`def answer():\n    return 42\n`。调用真实edit_file，用合法old_string匹配return行，将new_string设为历史省略标记，执行器返回成功；“应拒绝历史标记”的断言失败。因此防护不能只检查write的新建文件，还必须检查edit写入的替换正文。此项是已确认根因的影响范围扩展，未声称复测任务里也实际发生过这类edit污染。

### B. 实时显示仍与内部预算共用可清空的实报变量

`compaction.rs::compact_projected_send_view`在请求指纹不匹配时执行`state.last_step_usage = None`。后续预算和`emit_context_usage_live`同时使用此变量；`loop_.rs::attach_usage`也把同一字段交给最终保存。

最小运行：模型返回一次大文件write、一次edit，各带90000输入+10输出实报；第三次请求准备时较旧write参数被精简。捕获的三次实时数值为338 → 90021 → 8503，窗口始终200000，未触发上下文摘要。第二个数值是实报加工具回执增量，第三个数值已退回纯估算。预算失效本应只影响下一次请求预算，不应删除“最近一次接口实报”并让显示重新估算。

这说明8697a218只绕过了刷新面板时的指纹校验，没有完成底层数据生命周期分离。若后续未取得新的完整实报，清空后的字段也无法再提供给保存层；这一存储风险来自调用链检查，此次最小测试直接验证的是实时显示回退。

### C. 有额外请求参数的正常新实报会被误当成来源不明

`usage_anchor.rs::from_request`对非空extra_body/provider_options直接返回None，即使设置的仅为temperature。当前实现又把API格式仅存在request_identity里，没有独立保存实报的计数口径。

最小用例：已知OpenAI调用配置extra_body.temperature=0.5，实报输入90000、输出100，其中缓存80000。实际走同一指纹创建与面板选择函数，预期显示90100，结果为(None, 0)，落入整体估算。缺少指纹不代表缺少实报，也不代表当时不知道调用协议。不能把这种新数据当作无法判断历史缓存口径的旧数据。

应分别保存测量值、测量时的协议口径和预算适用状态，避免一个指纹条件同时控制三件事。

## 核实结果

### 1. 测试输出采集和管道状态：已证实

本次第58、59、60轮分别运行同一组unittest并接tail、head、grep，中间没有修改代码。工具耗时分别32840、8541、32934ms，总计74.315秒；后两次额外41.475秒。head还可能提前关闭管道，因此不能说三次都完整执行了整个测试集。

三次结果都是`exit_code: 0`，输出却包含测试失败。`src-tauri/src/native_tools/shell.rs::build_shell_command`直接调用Git Bash的`-c`，未启用pipefail；返回的是整个shell命令退出码。用同一Git Bash运行`false | tail -1`得到0，加`set -o pipefail`得到1。这是失败被管道末端掩盖，并非Kivio将收到的非零码改为0。

同文件已有大输出保存完整日志的实现（超过16KiB），但模型在命令中先head/tail/grep后，工具只能收到过滤过的输出，无法恢复原始测试日志。因此不能只新增一个“保存长输出”的功能就声称解决；需要让测试原始输出可复用，并保留原测试进程状态。pipefail单独也不能解决分号后成功命令覆盖前面失败的问题。

### 2. 自制测试工具返工：已证实

第60轮错误来自tests/support.py将正常HTML统一交给json.loads；第62轮才改为_maybe_json。第61轮修复调用本身还因缺失old_string失败。第75轮自制walkthrough.py又发生global BASE声明错误，第86/88轮DOM stub检查失败后继续修工具。

这些不能一概计入“发现产品缺陷”。本次新增/编辑tests路径18次、tools路径9次，其中包括正常开发，不应全算浪费；但确实存在可定位的测试工具自身返工。

### 3. 浏览器能力没有探测：比原分析更明确

本次工具参数中没有Playwright/Puppeteer/Selenium可用性探测，却在最终答复中写“环境无Playwright”。

上次第52轮成功导入`C:/Users/11028/AppData/Roaming/Python/Python314/site-packages/playwright/__init__.py`，后续browser_walkthrough.py记录有29/29走查通过。本次调查又在相同任务目录、通过相同Git Bash和`C:/Python314/python.exe`成功启动Playwright Chromium，对本地静态button执行click并读回改变后的文本；没有安装或联网。

因此“工具不存在”没有依据，已有证据反而显示工具可用。错误的能力判断让本次转向Chrome参数、截图和自制DOM测试，最终缺少真实点击回归。

严格按本次第93–133轮工具开始/结束时间计算为221秒（3分41秒），不是精确的3分48秒；若包括轮前后的模型等待，区间会不同。该阶段包含真实CSS/JS修复，不能把整个时段都算为浪费。

### 4. 停止条件和验证复用：部分成立，须区分验收要求

第135轮pytest与unittest各跑同一组102个测试，总耗时68.634秒。第153轮又运行pytest，测试输出33.26秒通过；两轮间没有修改业务代码，只有文档、截图及临时产物清理，未提供重跑同套测试的新理由。

但“135轮后都应直接结束”不成立：题目要求重启后验证持久化，第137–141轮包含这项真实服务验收。单元/API测试全绿也不等于浏览器点击验收完成。

当前prepare.rs的工作提示要求交付前验证、失败后修复重验，但缺少“检查覆盖哪些要求、哪些变更使结果失效、没有新变更就复用已通过结果”的明确约束。本次goal_state为空，不能归因于goal evidence失效规则触发重复验收。

### 5. 参数保护粒度：已证实，但不是全部上下文的解释

`src-tauri/src/chat/agent/argument_replay.rs`在assistant消息包含reasoning_items/signature等键时跳过整条消息；原生ModelMessage的reasoning_item在兼容消息转换中成为reasoning_items。

本次14个达到8KiB阈值的write/edit参数中，11个所在assistant带原生reasoning item，合计174550字节；其余3个合计47667字节。整条消息保护确实限制了参数精简覆盖面。字节数不等于可节省tokens，减少历史发送也不等于减少首次生成代码的输出量。缩小保护范围必须按实际协议验证，不能直接删除推理项或签名。

## 额外发现与归因边界

1. 批量工具调用减少：额外工具从107到167，同时同轮多工具批次从12轮降到4轮，模型请求增加69次。不能仅凭这两轮认定是调度器强制串行或某项修改必然造成。
2. 本次测试规模由上次42个增加到102个，但真实点击回归反而缺失；验证投入与验收覆盖没有对齐。测试数更多本身不是质量或效率提升的证明。
3. 本次24个历史图片part、更多工具调用与355440字符的原始调用参数都会占用历史；不能把最终239K全部归因于受保护的174550字节。
4. 两次模型执行计划、代码、测试数量均不同。确定存在的重复工作可以单独指出，但无法精确将多出的60秒分摊给每项代码改动，也不能承诺修掉某一项就降至170K。

在修复上述占位参数污染之后，再处理测试日志和真实退出状态、本地浏览器能力探测与验收覆盖、已有检查结果的复用及停止条件。当前不应直接扩大占位式参数精简的覆盖范围。
