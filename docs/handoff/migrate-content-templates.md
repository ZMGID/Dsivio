# M1：图片模板、视频模板迁入内容管理

状态：M1 代码迁移与自动验证已完成（2026-09-22），已同步主工作区；按约定未执行浏览器或真实桌面验收。所属清单：[Workbench 开发清单](../workbench-tasks.md) 的 M1。

## 目标与完成范围

把原图片、视频工作室的模板管理迁到 Workbench「内容管理」，提供两个独立入口：**图片模板**、**视频模板**。用户能读取已有模板、查看和编辑、导入导出；新入口直接使用独立模板读写能力，不经过旧工作室任务或视频 Python worker。

这是一次模板管理迁移，不是图片、视频全部迁移。AI 制作模板、换品试做、反馈改规则、生成后存为模板的入口，在后续 M2 / M3 接入同一模板负责人。本任务不做生成流程，不做新工作流引擎，不提前删除原图片、视频生成业务。

## 已确定的要求

- 简单直接，复用现有规则、文件格式和全局组件。一个模板动作在所属模块读得清楚；不增加通用模板平台、仓储接口层、控制器套娃或多套状态。
- 两类模板分别呈现、分别保留数据结构；只共享确实重复的轻量展示或文件操作，不强行统一图片槽位与视频镜头。
- 模板读写只有一个实现。旧工作室在过渡期还需要读写时，调用新的模板负责人；兼容命令只允许薄适配，不再保留另一份保存逻辑。
- 新能力与旧执行引擎无依赖。不能把 `image_studio_bootstrap` / `video_studio('bootstrap')` 包一层就当迁移，也不能把整个旧工作室嵌进内容管理。
- 保留用户模板和引用素材。第一版继续读写原数据目录即可，不为更名搬迁磁盘文件，不改用户真实数据作测试。
- 不使用浏览器或 UI 自动化，不调用付费模型。页面复用现有 Workbench 外框和全局控件，只做本任务需要的界面，不改其他布局和主题。

## 实现任务

### 1. 后端模板读写迁归内容管理

在合适的模板模块中承接图片与视频的列出、读取、保存、导入、导出。可直接用一个小模块加两类数据实现，按真实职责决定是否分文件；不要为了目录对称制造层次。使用带类型的 Tauri 命令与现有协议导出机制。

图片复用并迁出已有扫描、校验、素材复制和内置模板处理。`template.json`、`record.json`、模板 ID、`directory`、槽位次序及 `example/refs/refs_by_kind` 相对引用必须可读。smart/replace 规则分别保持；编辑内置模板另存为用户模板，不覆盖内置资源。导出必须携带模板引用的素材，重新导入后仍可使用。

视频把模板文件读写迁为 Rust 文件操作，管理动作不启动 Python/Node/MCP。兼容旧 JSON 的 `script/full_video_prompt/prompt_pattern`、`shots/shot_breakdown`、`spec/source` 和 `kind/reference_template/validated_from`。展示归一化不能在保存时丢掉未编辑的原始字段，也不能把未验证参考模板自动升级成生成模板。保留内置模板的正常可见性，不覆盖用户同名修改。

保留现有必要的路径、模板结构和引用检查，复用原子写入；不要为假设场景增加重试与兜底链。失败应返回可解释错误，不表现为保存成功。

### 2. 两个独立页面

在 `content/` 下新增图片模板页和视频模板页，注册到 `registry.ts`。使用稳定且直白的路由 id，例如 `image-templates`、`video-templates`；补齐现有支持语言的标签。首页、侧栏和搜索继续从注册表派生，不另写功能枚举。

各页提供模板列表、必要预览/详情、编辑保存、导入、导出。优先复用原模板管理的可用字段与交互，迁出其独立部分；避免把原大型工作室组件作为依赖，也不把原始 JSON 编辑器作为唯一业务界面。

这批不添加无功能的「生成/试做/应用」按钮。后续业务直接通过模板 ID 读取同一份模板；暂未接通的生产跳转不伪装可用。

### 3. 旧调用方收拢

迁移旧工作室尚需使用的模板读写到新负责人，移除重复实现。原有「模板库」管理入口改为进入对应内容管理页；原生成表单中的模板选择可以保留，数据来自新接口。保留现有未迁移业务的可用性。

`freeze`、方案提取等仍依赖旧生成 Task 的业务动作，允许本轮仍归旧业务模块；其模板最终保存应汇入新模板负责人。标明这些后续迁移点，不在本任务重写生成流程。
