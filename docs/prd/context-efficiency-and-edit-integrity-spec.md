# 内置运行时：上下文效率与文件修改可信度

日期：2026-09-14。范围：Kivio 内置运行时。本文将已完成的会话复核与 Research 调查转成实施规格；不表示实现已完成。此前计数优先级修复 `4e3141a2` 为本规格的行为基线。

## Problem Statement

用户在同一复杂应用构建任务中看到 Kivio 最后一轮上下文为269,150 tokens，OpenCode为168,948，DSH为176,896。旧估算覆盖实报的问题已修复，但Kivio仍存在成功文件操作回显冗长、无关查询污染上下文、局部编辑被显示为大面积改写的问题。用户尤其担心整文件覆盖、大段修改和返工增加耗时、消耗并损害已有成果。

实测确认的案例：

- 仅写入/编辑的工具轮，Kivio下一请求输入净增长合计29,397 tokens，OpenCode为1,263。两边操作内容和轮数不同，此差额是诊断证据，不是承诺节省量。
- 一次检查临时目录清理情况的命令返回18,106字符的无关目录列表，下一请求输入净增10,218 tokens。
- 一次包含六处局部替换的文件修改，最小行差异为新增30行、删除20行，界面及工具回显却报告新增1,088行、删除1,078行。原因是diff算法在跨度较大时将整个中间区间降级为删除再新增。
- 14次write中12次属于首次创建；两次覆盖中，一次是实现入口占位文件，另一次是对刚创建的存储模块再次整份写入。不能把首次创建或所有大文件输出都判为浪费。

源码检查还发现两类独立风险：旧实报缺少模型及请求配置适用范围检查；固定90%压缩阈值没有明确协调实际输出预算。它们尚未证明解释本次差额，实施时应先通过行为测试复现。

## Solution

用户应得到更少冗余、更可信的文件修改和上下文统计。模型修改现有文件时优先做明确、局部的编辑；用户仍可完成必要的整文件创建或重构。成功工具回执简短、失败和诊断充分，完整diff和长日志可追溯。局部修改不能被算法伪装成千行重写。

上下文显示以适用的API实报为准，只估算尚未测量的变化；切换配置后不冒用旧值。运行时根据提供方的实际输入、上下文和输出限制决定是否整理历史，保留协议要求的推理与工具配对。

最终以“文件结果正确、关键诊断保留、实际请求冗余下降、统计来源诚实”为验收标准。不能用更早的有损压缩或降低推理强度来追平某个上下文数字。

## User Stories

1. 作为用户，我希望修改现有文件时优先采用局部编辑，以便减少不必要的整文件覆盖。
2. 作为用户，我希望首次创建文件可以完整写入，以便正常构建应用。
3. 作为用户，我希望明确要求的整体重构仍可执行，以便优化规则不阻碍合理工作。
4. 作为用户，我希望Agent保留未涉及的代码，以便小修复不会意外破坏其他功能。
5. 作为用户，我希望编辑所依据的内容发生变化时收到明确失败信息，以便Agent重新读取后处理而非覆盖新内容。
6. 作为用户，我希望多处小修改显示成真实的局部差异，以便审阅时能准确判断影响范围。
7. 作为用户，我希望diff增删行统计与实际匹配结果一致，以便不会将小修改误认成千行重写。
8. 作为用户，我希望超大文件的diff计算保持响应性，以便审阅不会卡死。
9. 作为用户，我希望无法完整计算diff时看到明确状态，以便不会把粗略结果当成精确统计。
10. 作为用户，我希望界面保留完整且可查看的变更信息，以便精简模型上下文后仍可审阅成果。
11. 作为模型工具调用方，我希望成功写入只返回必要的结果摘要，以便不必再次接收刚生成的代码。
12. 作为模型工具调用方，我希望失败、部分成功及重要警告明确返回，以便不会误以为任务已经完成。
13. 作为模型工具调用方，我希望测试失败和编译错误的关键诊断被保留，以便可以继续定位问题。
14. 作为用户，我希望验证清理结果时只查询本次涉及的路径，以便无关文件列表不进入上下文。
15. 作为模型工具调用方，我希望目录和搜索结果有明确范围及数量控制，以便优先获得相关信息。
16. 作为模型工具调用方，我希望长日志提供可恢复的全文位置和定向读取方式，以便摘要不够时能够补读。
17. 作为用户，我希望长工具结果的处理符合其类型，以便不会为省字数丢失代码或错误上下文。
18. 作为用户，我希望API实报不会被更大的字符估算覆盖，以便看到可信的占用数字。
19. 作为用户，我希望实报之后的新增内容单独标示估算，以便了解数字的确定程度。
20. 作为用户，我希望切换模型后旧模型的实报不会被当成当前实报，以便避免错误决策。
21. 作为用户，我希望切换提供方或API格式时用量口径保持正确，以便缓存与输出不会重复计算。
22. 作为用户，我希望启停工具、切换助手或修改提示词后统计反映变化，以便隐藏配置变化不会造成低估。
23. 作为用户，我希望旧会话升级后仍可查看和继续，以便新增用量元数据不会破坏历史记录。
24. 作为用户，我希望清空上下文、压缩和异常恢复后的用量标签保持准确，以便不沿用失效状态。
25. 作为用户，我希望接近上下文上限时为回答留出合适空间，以便避免本可预防的输出截断或请求失败。
26. 作为模型工具调用方，我希望压缩和回放保留提供方要求的推理及工具调用关系，以便不会因省tokens而破坏协议。
27. 作为用户，我希望减少冗余时兼顾缓存命中，以便上下文变短不以显著增加重复输入费用为代价。
28. 作为评测者，我希望各Agent使用隔离的端口、数据库和临时路径，以便环境冲突不被误判成Agent效率问题。
29. 作为评测者，我希望记录模型、协议、推理强度和人工干预，以便结果可比较、可复核。
30. 作为维护者，我希望回归测试检查文件、实际模型请求和显示结果，以便不是只测试内部辅助函数。

## Implementation Decisions

### 1. 文件创建、局部编辑和整体替换

- 内置文件工具与运行时指令统一采用“创建可完整写入、已有文件默认局部编辑”的策略。工具描述应明确用途、编辑失败后重新读取的路径，以及整体替换适用于明确重构等情形。
- 优先复用现有精确匹配、歧义拒绝和文件变更锁。针对用户或其他进程在读写间修改文件的场景，验证现有保护；不足时补充写入前一致性验证，不扩大为新的通用权限流程。
- 不按固定文件大小禁止write，不因输出长就强迫把首次创建拆成多次追加，不要求用户逐次批准日常编辑。
- 不把模型的一次整份输出自动改写成未经验证的补丁。若实现自动优化，最终文件必须与原请求一致，且满足并发修改保护；首版优先使用正确工具选择及既有编辑语义。
- 是否发生返工按执行记录、修改范围与失败原因判断。不得将“每次write都算浪费”作为指标，也不得承诺通过工具规则消除模型推理差异。

### 2. diff与变更统计

- 修改文件的执行结果、供用户审阅的diff、供模型读取的回执分别承担各自职责，避免把展示载荷直接当模型结果。
- 替换现有因计算矩阵超限而将整个中间区域全部删除/新增的回退策略。可选用支持局部匹配的成熟算法或稳定分块策略；不在规格中固定具体依赖。
- 六处局部编辑的大文件案例必须得到真实局部变化。短文件、重复行、多处相隔很远的编辑、中文和换行格式都应正确处理。
- 有明确的计算资源上限；无法生成可靠完整diff时返回“未完整计算”等状态，不能把粗粒度替代值作为精确增删数。模型成功回执仍以真实文件操作结果为准。
- 尽量保持现有结构化结果契约。若需新增完整性状态，提供兼容默认值并同步前后端协议；不得把旧记录未经核实地升级为精确结果。

### 3. 模型可见的工具结果

- 原生write/edit成功回执只包含操作、路径、必要变更摘要和警告，不附带代码diff。noop、失败、部分成功与诊断须可区分。
- 完整diff继续用于用户审阅。回执精简不能改变磁盘内容、已执行操作的语义或UI审计能力。
- 长日志沿用全文外置及可定位读取能力，按结果性质保留关键内容和退出码；目录列表优先数量统计与有限样本，错误输出保留关键首尾，读取代码支持精确范围。
- 查询指令强调限定目录、模式和数量；清理确认使用本次创建的明确路径。不能把跨整个临时目录的模糊查找当作默认验证步骤。
- 当前全局工具输出上限已经存在；本期优化其调用策略及结果类型处理，不将“无截断”作为假设，也不强制所有结果统一截为2K字符。
- MCP结构化输出遵守其既有契约。原生工具回执改动不得顺带删除外部工具的重要结构化内容或协议要求字段。

### 4. 实报锚点的适用范围

2026-09-14 回归修正：界面保留最近一次实际响应的实报，未计量增量单独估算。请求指纹只决定该测量能否用于下一次请求的预算判断，不得因指纹缺失或不匹配清除已有实报。响应的 token 计数协议独立记录，不能依赖预算指纹或当前可变的提供方设置来解释缓存计数。以下身份适用性约束针对请求预算；真正压缩、删除上下文后的旧测量仍须失效。

- 继续遵守已修复规则：有效实报优先，其后新增内容增量估算，无适用实报才回退；不得重新引入取全文估算与实报较大值的逻辑。
- 锚点至少关联实际提供方、模型标识、API格式、上下文边界，以及影响请求的系统指令与工具配置版本。应从实际请求视图取得身份信息，避免只依赖可变的会话设置。
- 指纹可覆盖配置及序列化版本，不能保存密钥。动态提示若影响请求也必须纳入适用性判断；不要将仅展示状态纳入而导致无意义失效。
- 使用同一提供方换模型、跨提供方切换、变更API格式、工具集合/schema、助手、挂载提示、知识上下文或压缩边界时重新判定锚点。
- 已测量历史值仍可保留为“上次实报”，但不能冒充变更后的当前实报。未测量部分使用明确估算标签；新请求取得实报后恢复对应身份的权威值。
- 旧消息没有来源身份时采用兼容读取，无法证明适用就诚实回退，不根据当前会话provider/model伪造历史来源。
- 实时事件、轮末快照、刷新和重新打开会话必须共享该规则；缺失usage、精简恢复和被改变的发送视图不能借用不适用锚点。

### 5. 上下文与输出预算

- 依据实际模型/协议提供的输入上限、总上下文上限与有效输出额度计算请求预算；固定90%不能作为唯一条件。支持不同提供方对输出预留的不同约束，避免重复扣除或套用其他协议口径。
- 压缩前后的系统指令、工具定义及近期保留消息必须在预算内。无法通过压缩解决时返回明确结果，避免不断压缩重试或静默继续发送已知超限请求。
- 元数据缺失时采用有标识的保守后备策略；兼容已有用户显式设置，不能把网页上最新型号上限自动套给旧会话别名。
- 保留提供方要求的历史推理和工具调用/结果配对。只有按其能力有效重建的压缩历史才可用于发送；不依赖其不支持的服务端存储或自动压缩参数。
- 本次269K并未证明触发预算风险；此项以边界测试验收。不得设定170K或200K为所有模型统一的压缩目标。

### 6. 测量与实施顺序

- 先处理局部编辑策略、diff真实性和成功回显，再处理无关查询与类型化结果预算；随后补齐锚点适用性和输出预留边界。
- 从现有测试和日志提取脱敏、可复现的小型样例。验收应记录模型可见字符/字节、实际或明确标注为估算的tokens、累计输入/缓存/输出、错误重试与产物质量。
- API返回token总数通常不能精确分配到每个字段。相邻请求差额必须说明包含消息封装及其它变化，不将组间统计差额当作反事实保证收益。
- 准备隔离复测的执行清单：独立端口、数据库、临时路径和结果目录；检查端口归属并记录模型/协议/参数及人工干预。不得自动读取或修改其他参赛者的会话、代码或常驻服务。
- 不将研究或规格生成视为启动付费三家复测的指令。首轮完成依靠确定性本地验证；若用户确认增加复测验收，再按约定执行。

## Testing Decisions

测试以可观察行为为准：磁盘最终内容、工具结果、真正传给模型的请求、上下文事件与必要的界面标签。避免仅断言某个内部函数被调用或字符串实现细节。

主验证边界沿用现有Agent循环及工具执行入口，接现有本地模拟模型服务和临时工作目录。文件算法的边界只增加必要直接测试；界面仅补来源标签、diff完整性等后端测试无法覆盖的契约。此前已有真实usage优先、上下文事件、文件锁/差异、结构化工具结果与前端用量更新测试可复用。

| 验收情形 | 可观察通过条件 |
|---|---|
| 大文件六处局部编辑 | 以脱敏样例复现约1300行跨区域修改；磁盘内容符合六处替换，差异为+30/-20，保留1283行相同内容，不显示+1088/-1078 |
| 计算资源受限 | 大文件不导致无界内存或明显卡死；不能计算可靠diff时给出明确不完整状态，不报告伪精确统计 |
| 文件操作语义 | 创建、精确编辑、合理整体替换均成功；匹配歧义或内容过期时不意外覆盖文件；确认现有并发修改保护实际有效 |
| 局部编辑指引 | 实际工具schema/运行时指令明确创建与修改用途；不引入任意大小禁令，也不强迫首次创建使用小块追加 |
| 成功回显 | 在多轮实际请求中，write/edit回执不携带diff正文；用户结构化审阅数据仍含正确diff，文件不变 |
| 错误与警告 | 注入失败、部分成功或警告，模型能够收到真实状态与恢复线索；不能一律替换成成功摘要 |
| 长日志与目录列表 | 大量UUID目录、长错误日志、单行大输出均受适用预算控制；没有反复把全部结果回传，全文路径可访问，关键错误与退出码保留 |
| 目标范围 | 隔离清理样例只涉及登记的临时路径；验证其指令与工具组合不会要求枚举整个共享Temp；不靠含糊关键词过滤猜测所有权 |
| 推理回放 | 根据实际提供方协议检查请求中必要推理及工具配对，既不漏传也不因展示副本发送两份 |
| 实报优先 | 原案例269150对339433仍采用适用实报；其后新增内容仅计一次并显示混合来源 |
| 锚点配置变更 | 参数化覆盖同提供方换模型、跨提供方/API、启停工具与schema变化、助手/指令变化；旧值不标当前实报，新实报到达后恢复 |
| 旧会话与恢复 | 缺来源身份的历史会话可加载；无usage、压缩、清空、精简恢复和重启后不沿用错误锚点或标签 |
| 预算边界 | 覆盖小窗口、大输出额度、独立input上限、元数据缺失、大工具结果、压缩失败；请求与有效预留符合该协议约束且无无效重试循环 |
| 前后端契约 | 结构化diff状态和三类用量来源在实时/刷新后保持一致；新增字段兼容旧消息，生成的协议定义同步 |
| 效率与正确性 | 使用相同固定样例对比模型请求，证明已知回显与无关结果减少；仍能完成样例操作，保留必要诊断，不以计数估算下降替代实际载荷验证 |

运行受影响的后端测试、前端契约测试、类型和协议一致性检查。仅展示或文案变化不要求新建完整UI自动化套件。性能验证使用代表性规模及明确记录的资源预算，避免依赖脆弱毫秒断言。

## Out of Scope

- 重新实现或改写OpenCode、DSH等外部CLI代理；导入的原生会话按现有ADR继续由其原CLI运行。
- 删除协议要求的历史推理、降低用户的high强度、通过忽略工具或错误缩短任务。
- 为追平169K设置固定全局压缩阈值，或承诺100K差额全部可消除。
- 将所有整文件写入禁用、要求用户逐次批准普通修改、自动撤销用户已有改动。
- 重做上下文指示器整体视觉设计，或把调试计数塞入普通用户操作流程。
- 改变子代理身份、任务生命周期或已有权限语义。
- 自动重跑付费对照实验、重新给三家成果评分、操作其它参赛者服务，或将全部用户会话上传到issue。
