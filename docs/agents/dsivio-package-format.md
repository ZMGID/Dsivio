# Dsivio 包规范

所有经过维护者试跑的功能统一叫包（Package），放在 GitHub 上更新，不塞进 Dsivio 安装包。

## 统一结构

```text
packages/包名/
  INSTALL.md       # 点击安装时发送的原文
  DSIVIO.md        # 使用时挂载的指导正文
  market.json      # 市场名称、分类、简介和对话示例
  assets/          # Logo、展示图片等，有需要再放
  files/           # 自制包的完整功能文件，有需要再放
```

两种包用同一套结构和操作，区别只是功能文件从哪里来，不需要另加类型字段。

## 第一种：使用网上现成项目

包里放两份文档、市场 JSON 和需要的展示素材。项目本身留在原仓库。

INSTALL.md 写清项目链接，让 Agent 阅读项目 README，安装项目和必要依赖。需要固定版本时写上版本。

例如：

> 给自己安装 https://github.com/geeklee/srt-whiteboard-animation 这个项目。阅读它的 README 和 SKILL.md，安装 Skill，并准备必要的 Python 环境和依赖。

## 第二种：我们自己制作的包

除了上述文档和展示信息，把实际功能文件完整放进 files/，随包上传到 GitHub。包括需要的 Skill、代码、运行脚本、模板、素材和依赖清单；保留它们原有的目录结构及相对引用。

INSTALL.md 指向本包的 files/，说明如何安装和准备依赖。例如：

> 安装本包 files/ 中的功能。阅读其中的 README，安装 Skill 并准备所需依赖。

完整上传的是运行所需的源文件，不是本机的虚拟环境、node_modules、缓存、密钥或生成结果。功能自身的运行脚本可以随包提供，不额外制作一套市场安装脚本。

## 两份文档怎么写

INSTALL.md：安装来源、必要依赖，以及安装时要做的配置。点击安装只发送这份文档原文，不自动追加指令、另一份文档或密钥。

DSIVIO.md：何时优先使用这个包、怎么使用，以及需要的 Dsivio 说明。使用时挂载正文，不作为用户消息发送，不额外拼接包提示词。

需要读取服务配置时，在相应文档写一句：

> 需要模型接口和密钥时，调用 kivio_inspect(topic="capabilities") 读取能力配置。

由 Agent 按需主动读取，不把密钥直接注入或写进发布包。

文档使用简短的普通文本即可。不要求额外的 USAGE.md、VERIFY.md，也不要求作者编写统一验收脚本。

## 市场展示

market.json 沿用现有 manifest 和 example 两部分，填写名称、分类、简介、简短使用提示及对话示例。图标用包内相对路径，例如 assets/logo.png，展示时统一裁成圆角。示例只用于页面展示，不发送给 Agent。

有官方 Logo 就用官方素材；没有时可制作功能图标，但不冒充官方 Logo。

## 使用与发布

开关控制包相关 Skill 的启用与关闭。安装和使用都通过对话完成，两种来源不增加额外页面或操作步骤。

维护者先试跑，再发布到 GitHub。catalog.json 是市场总目录，放在 packages/ 下，不属于某个包。正式条目指向包所在目录和固定提交；更新包后再更新目录指向。

开发时 DSIVIO_MARKET_DRAFT_DIR 可以指向单个包，也可以指向 packages 总目录同时预览多个包。
